## 0. Уточнення скоупу — ЧИЮ документацію індексуємо

§8 v1.0 казав «RAG по доці» узагальнено. Треба розрізнити два різні боти,
бо вони мають різну аудиторію і зовсім різні джерела:

| | Внутрішній doc-QA (цей документ) | Клієнтський Sales/Support (STRATEGY §4, Фаза 3) |
|---|---|---|
| Аудиторія | Ти / Claude Code / Claude AI — питання про проєкт | Клієнти Shopify-магазинів — питання про застосунок |
| Джерела | `CLAUDE.md`, `README.md`, `docs/DECISIONS.md`, `docs/specs/*`, `docs/prompts/*` | Онбординг, FAQ, документація застосунку — **ще не існує** |
| Складність | Просте питання-відповідь по markdown, без агентного циклу | Тікети, ескалація, Shopify Billing-контекст — Фаза 3 |

**Рішення цієї спеки: робимо внутрішній doc-QA.** Клієнтської документації
фізично ще немає (немає навіть UI застосунку) — RAG по неіснуючих джерелах
писати нема сенсу. Це узгоджується з §8 v1.0 («джерело знань — усе, що вже є
в репо»), просто робимо явним, що це не прототип Sales/Support Agent з Фази 3,
а інструмент для тебе й агентів проєкту («що ми вирішили про X», «яка схема
CanvasJSON», «чому SVG не в тракті»). Природний place для нього пізніше —
вбудувати той самий retrieval-шар у Фазу 3 бота, просто на інших джерелах.

## 1. Джерела знань

Індексуємо статично всі `.md` файли за списком директорій (без винятків —
простіше й чесніше, ніж allowlist окремих файлів, який доведеться підтримувати
руками):

```
CLAUDE.md
README.md
docs/DECISIONS.md
docs/specs/*.md
docs/prompts/*.md
docs/research/*.md   (порожньо зараз — підхопиться автоматично, коли з'явиться)
```

`STRATEGY.md`/`OPERATING-MODEL.md` — навмисно НЕ в скоупі: вони приватні,
поза публічним репо (README.md вже це фіксує). Якщо потрібні для QA — окреме
рішення Антона, не мовчазне додавання.

## 2. Chunking

Ділимо кожен `.md` файл по заголовках другого рівня (`##`) — це вже природна
одиниця сенсу у всіх наявних доках (спеки й DECISIONS.md структуровані саме
так). Метадані на чанк: `{file_path, heading, text}`.

- Якщо секція `##` довша за ~1500 токенів (рідкість у наявних доках, але
  можливо для великих спек) — додатково ріжемо по `###` всередині неї.
- `docs/DECISIONS.md` — особливий випадок: там немає `##`, це плаский список
  `- **дата · рішення.**`. Кожен bullet — окремий чанк (це вже атомарна
  одиниця рішення, дробити далі нема сенсу).

## 3. Retrieval — без векторної БД (навмисно, §8 v1.0)

Простий keyword-скоринг (BM25-подібний, `rank_bm25` або ручна TF-IDF на
токенізованих чанках), **не embeddings, не Supabase pgvector**. Причини:

- Обсяг корпусу — одиниці документів, десятки чанків. Векторний пошук —
  оверінженіринг для цього розміру.
- Anthropic API не дає власного embeddings-ендпоінту — довелось би тягнути
  сторонній провайдер лише заради цього, зайва залежність у Фазі 1.
- Якщо корпус виросте (Фаза 3, клієнтська документація) — тоді й
  переоцінимо: Supabase вже в стеку (DECISIONS.md), pgvector підключити
  дешево, коли буде виправдано обсягом.

`k = 5` — топ-5 чанків у контекст промпту. Обґрунтування: наявний корпус
малий (кожен документ — кілька KB), 5 чанків з запасом покриває навіть
питання, що зачіпають 2-3 різні спеки одночасно, і лишається під лімітом
контексту з запасом.

## 4. Формат виклику Claude Opus 5

Один виклик, без агентного циклу (це RAG, не ReAct — узгоджено з §8 v1.0).
Модель — `claude-opus-5` (дефолт проєкту, DECISIONS.md).

### System prompt (чернетка)

```
Ти відповідаєш на питання про проєкт Vektralogos, спираючись ЛИШЕ на подані
фрагменти документації. Не використовуй жодних знань поза ними.

Правила:
- Якщо відповідь є у фрагментах — дай пряму відповідь, коротко, і вкажи
  джерело: [файл: docs/specs/....md, розділ: "...”].
- Якщо фрагментів недостатньо для впевненої відповіді — прямо скажи
  "У документації проєкту цього немає" замість вигадувати.
- Якщо фрагменти суперечать один одному (напр. стара спека і DECISIONS.md
  з новішим рішенням) — вкажи обидва і зазнач, який документ новіший
  (за датою у назві файлу чи в тексті), якщо це видно з чанків.
- Відповідай тією мовою, якою поставлено питання.
```

### Вивід

Звичайний текст (не structured output — це кінцева відповідь людині, а не
крок pipeline). Формат цитати джерела — узгоджений з copyright-практикою
проєкту (немає дослівного цитування великих шматків; переказ своїми словами
з посиланням на файл).

## 5. Інтерфейс — CLI (мінімум для Фази 1)

```bash
python -m server.cli ask "чому CMYK через Ghostscript, а не ReportLab native?"
```

Без HTTP-ендпоінту, без вебхука — це внутрішній інструмент, REST/API шар
з'явиться природно разом з Shopify-app каркасом (не в скоупі Фази 1).

## 6. Acceptance criteria

- [ ] На питання «яка канонічна CanvasJSON схема?» — відповідь посилається
      на `server/schema.py` через `docs/specs/VEKTRALOGOS_SPEC_Phase0-PDF-Pipeline_v1.1...`
      (не вигадує деталі поза чанками).
- [ ] На питання поза корпусом (напр. «яка ціна на Zepto?») — модель прямо
      каже «немає в документації», не вигадує.
- [ ] На питання, де є і стара спека, і новіше рішення в DECISIONS.md —
      відповідь відображає АКТУАЛЬНИЙ стан (напр. про `element_index`), не
      застарілу версію з чернетки.
- [ ] Індексація підхоплює новий `.md` файл у `docs/specs/` без зміни коду
      (динамічний скан директорій, не хардкоджений список файлів).
- [ ] Unit-тест на chunking `DECISIONS.md` окремо від retrieval (перевірити,
      що кожен bullet — окремий чанк).
