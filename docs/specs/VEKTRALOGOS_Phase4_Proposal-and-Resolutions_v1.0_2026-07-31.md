## 2. Схема approval-гейта (як бачить виконавець)

```
... [prepare_diff] --> [approval_gate] --(approve)--> [open_pr] --> END
                            │  (interrupt_before: граф зупиняється, чекає людину)
                            └--(reject)--> [finalize(rejected)] --> END
```

- `approval_gate` — вузол з `interrupt_before`: граф зупиняється, віддає стан
  (diff + опис) на рішення людини; відновлюється з рішенням (`approve`/`reject`)
  через той самий `thread_id` (чекпойнт уже є).
- `open_pr` — ЄДИНИЙ вузол, що робить `gh pr create` (необоротна дія), і лише
  ПІСЛЯ явного `approve`.

**Термінальні статуси Ф4:** `applied` (PR створено) / `rejected` (людина
відхилила) / `needs_human` (як досі — воркер не впорався).

## 3. Milestone-розбивка

- **4a `chore/p4a-approval-trace`:** `approval_gate` (interrupt_before) +
  `open_pr` за `approve`; структурований JSON-трейс кроків графа.
  Acceptance: без `approve` — граф зупинений, `gh` НЕ викликано; після `approve`
  — `open_pr` викликається один раз; `reject` → `rejected`, `gh` не викликано;
  трейс містить усі пройдені вузли.
- **4b `chore/p4b-limits-evals`:** ретраї на впалому LLM-виклику (обмежені),
  per-run token budget зі стопом, мінімальні детерміновані evals.
  Acceptance: ретрай спрацьовує на змодельованому збою й здається після N;
  budget-стоп зупиняє прогін при перевищенні; evals-набір зелений на фікстурах.

   PR-payload» + ручне створення (тобто гейт є, але зовнішній виклик — ще ні).
   Рекомендація виконавця: **реальний `gh pr create` ПІСЛЯ approve** — інакше
   гейт нема що охороняти, а це і є навчальна ціль фази.

Після затвердження виконавець стартує з `chore/p4a-approval-trace`.
