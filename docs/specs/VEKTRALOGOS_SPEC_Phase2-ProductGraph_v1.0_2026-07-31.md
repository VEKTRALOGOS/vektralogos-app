## 1. Скоуп графа — два milestone

### Чому не одразу повний цикл

STRATEGY.md §3 Фаза 2 називає ціль одним реченням («Product Agent: фідбек →
план → генерація фічі/пресета → preflight-перевірка → PR»), але це
одночасно: (а) перше знайомство з LangGraph API, (б) перший LLM-крок, що
генерує код/фічі (новий клас складності, не був у Ф0–Ф1), (в) зовнішній
side-effect (PR). Змішувати «вчу граф» і «вчу генерацію фіч» в одному PR —
проти власної дисципліни проєкту «не прыгаем вперед» (STRATEGY.md §3, вступ)
і проти практики малих PR (`docs/DECISIONS.md`, підхід Ф1).

### Milestone 2a — `feat/p2a-preflight-graph`

Переписати `preflight_agent()` (Ф1, чистий Python-цикл) на LangGraph
`StateGraph` **без зміни поведінки** — той самий allowlist фіксів, той самий
фікспойнт-детектор, ті самі статуси (`ok/needs_human/no_progress/
max_iterations_reached`). Мета — не новий функціонал, а навчитись
графу на відомому, вже протестованому домені:

```
State: { spec, report, prev_signature, iterations, status }

[check_preflight] --(fixable є)--> [pick_and_apply_fix] --> [check_preflight]
       │
       └--(fixable немає)--> [finalize] --> END

[pick_and_apply_fix]: якщо sig == prev_sig -> [finalize(no_progress)]
[check_preflight] (за max_iterations) -> [finalize(max_iterations_reached)]
```

- Checkpoint після кожного вузла (`MemorySaver`, §3) — вчить API
  checkpointing, навіть якщо персистентність поки не потрібна функціонально.
- **Acceptance 2a:** усі існуючі тести `tests/test_preflight_agent.py`
  проходять і на graph-версії (той самий контракт входу/виходу); порівняльний
  тест «graph-версія і Ф1-версія дають однаковий `AgentResult` на одному й
  тому ж вході» — щоб довести еквівалентність, не регрес.

### Milestone 2b — `feat/p2b-product-graph`, після мержу 2a

Product Agent поверх графової дисципліни з 2a:

```
[ingest_feedback] -> [plan] -> [generate_feature_or_preset] -> [preflight_subgraph(2a)]
                                                                        │
                                          (ok) ─────────────────────────┼──> [prepare_diff] -> END
                                          (needs_human/no_progress) ────┘──> [finalize(needs_human)] -> END
```

- `preflight_subgraph` — граф із 2a, викликаний як вузол (LangGraph підтримує
  вкладені графи) — не переписуємо логіку вдруге.
- `generate_feature_or_preset` — ЄДИНИЙ вузол з LLM-генерацією коду/контенту
  в Фазі 2. Скоуп навмисно вузький на старт: генерація **пресету** (напр.
  новий набір кольорів/шаблон DesignBrief під сегмент клієнтів), НЕ довільна
  зміна коду репо. Повноцінна кодогенерація фіч — це вже ближче до
  Director-Worker делегування (STRATEGY §3 Фаза 3), не Фаза 2.

**Прийнято:** звуження «генерація фічі» → «генерація пресету» для 2b, як
запропоновано. Ширшу кодогенерацію свідомо лишаємо Фазі 3 (Director-Worker),
щоб 2b не перетворився на другий Director до того, як перший спроєктований.

## 2. Джерело «відгуків» (2b, `ingest_feedback`)

**Зараз:** синтетичний фікстур `docs/research/fixtures/competitor_reviews.md`
— 8–10 записів у форматі один-до-одного з тим, що очікується від Gemini
(STRATEGY §5: «Валідація: 1★-відгуки Customily/Zepto — частота скарги
"low-res замість вектора"»). Джерело контенту фікстура — вже описані в
STRATEGY.md жалоби конкурентів («експорт в мильний PNG замість вектора»),
не вигадані з нуля.

**Формат фікстура** (щоб парсер `ingest_feedback` не міняти, коли Gemini
здасть реальний ресёрч у `docs/research/`):

```markdown
## Review: Customily, 1★, 2026-XX-XX
> [дослівна цитата ≤15 слів АБО переказ — уникати копірайт-ризику навіть
> у фікстурі, привчаємо парсер одразу до paraphrase-джерел]
tags: low-res-export, vector-missing
```

`ingest_feedback` читає `docs/research/*.md` за тим самим `_DOC_GLOBS`-
підходом, що вже є в `support_bot.py` (§1 тієї спеки) — переюзаємо, не
винаходимо новий сканер.

## 3. Checkpoints/пам'ять

**In-memory (`langgraph.checkpoint.memory.MemorySaver`) для всієї Фази 2**
(2a і 2b). Обґрунтування — той самий принцип, що вже застосований до
support-бота (`rank_bm25` замість pgvector, DECISIONS.md): не тягнути
інфраструктуру наперед потреби.

Реальна потреба в persistent checkpoints (Postgres) зʼявляється, коли:
- Граф має переживати рестарт процесу (довгоживучий Director у Фазі 3), або
- Потрібна історія запусків для evals/спостережності (Фаза 4).

Жодного з цих факторів у Фазі 2 немає — Product Agent запускається,
відпрацьовує, завершується в межах одного процесу (CLI-виклик, як
`preflight-fix`/`ask`).

## 4. PR-вузол — diff, не автостворення

`prepare_diff` (2b) генерує:
- Змінений файл (напр. новий пресет `presets/<name>.json` або оновлений
  DesignBrief-шаблон) як реальний diff/patch на диску.
- Короткий опис для майбутнього PR (заголовок + чому + посилання на
  відгук(и)-джерело з `ingest_feedback`) — текстовий файл поруч, не
  публікується нікуди.

**Чому не `gh pr create` зараз:** відкриття PR — зовнішня, видима дія
(сповіщення, публічний артефакт у репо). Це саме той клас «необоротних
дій», для якого STRATEGY §3 Фаза 4 явно проектує approval-гейти,
моніторинг, ретраї. Робити для одного вузла Фази 2 ad hoc «чи можна
автостворювати PR» — дублювання Фази 4 наперед, без фреймворку навколо
(немає ще ретраїв, лімітів, трейсу — якщо генерація зіпсує diff, ніхто це
не зловить до автостворення PR).

Автостворення PR — природний, вже спроєктований кандидат на перший
approval-гейт у Фазі 4 (`chore/observability`), не зміна цієї спеки.

## 5. State schema (2b, чернетка)

```python
class ProductGraphState(TypedDict):
    feedback: list[FeedbackItem]        # з ingest_feedback
    plan: str | None                    # з plan
    generated_preset: dict | None       # з generate_feature_or_preset
    preflight_result: AgentResult | None  # з preflight_subgraph (2a)
    diff_path: str | None               # з prepare_diff
    status: Literal["ok", "needs_human", "no_feedback"]
```

`no_feedback` — новий термінальний статус: якщо `ingest_feedback` не
знаходить жодного релевантного запису (порожній фікстур/ресёрч ще не
надійшов) — граф зупиняється чесно, не намагається «щось згенерувати з
нічого» (той самий принцип чесної non-fixable-ескалації, що в Ф1 §5).
