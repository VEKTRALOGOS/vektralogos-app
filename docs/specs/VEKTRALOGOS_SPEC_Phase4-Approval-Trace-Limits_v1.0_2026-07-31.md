## 1. Схема гейта — без змін від пропозиції Code

Приймаю схему з розділу 2 вхідного документа
(`prepare_diff → approval_gate(interrupt_before) → open_pr | finalize(rejected)`)
і термінальні статуси (`applied`/`rejected`/`needs_human`) як канонічні.

## 2. Доповнення

### 2.1 Governance навколо `open_pr` (доповнення до резолюції #2)

Це перша дія системи, що видима зовні репозиторію (сповіщення, публічний
артефакт) — самé тому й перший гейт. Три додаткові вимоги, щоб гейт був
реальним контролем, а не формальністю:

- **Explicit confirmation, не "будь-яка клавіша".** CLI показує повний diff +
  опис PR і вимагає ввести конкретне слово (`approve` текстом, не `y`/Enter) —
  знижує ризик випадкового підтвердження.
- **Аудит-лог у трейсі (§3):** хто підтвердив (system user з `whoami`/env, не
  вигадуємо authentication-шар), коли (timestamp), який `thread_id`/diff-hash
  підтверджено. Без цього `approve` — непідзвітна дія.
- **На `reject` diff-файл НЕ видаляється** — лишається на диску (той самий
  шлях, що `prepare_diff` уже писав у Ф2b) для ручного review/PR пізніше.
  Тільки статус графа — `rejected`, артефакт живий.

### 2.2 Уточнення моделі взаємодії (доповнення до резолюції #3)

`MemorySaver` (рішення Фази 2, `docs/DECISIONS.md`) — **in-memory**, живе
лише в межах одного процесу. `interrupt_before` з ним працює **тільки якщо
підтвердження відбувається синхронно, в тому самому CLI-виклику** (граф
зупиняється → людина одразу відповідає в тому ж терміналі → граф
продовжується в тому ж процесі).

> [!IMPORTANT] Якщо мається на увазі асинхронна модель («граф ставить PR на
> паузу, я підтверджую через день окремою командою») — `MemorySaver`
> недостатньо, знадобиться персистентний checkpointer (Postgres/Supabase),
> що переглядає рішення Ф2 §3 («in-memory, Supabase — коли зʼявиться реальна
> потреба»). Ф4 і є та реальна потреба, ЯКЩО модель — асинхронна.

**Рекомендація:** синхронна модель (одна CLI-команда `python -m server.cli
propose-and-open-pr <feedback-source>`, всередині — весь граф до `approve`/
`reject` в одному процесі). Причини: (а) немає ще випадків, коли підтвердження
реально потрібне через день, а не одразу; (б) не тягнути Supabase-checkpointer
заради гіпотетичного сценарію, той самий принцип «не наперед потреби», що вже
застосований тричі (`rank_bm25`, `MemorySaver` у Ф2, тепер тут). Якщо пізніше
знадобиться асинхронний approval (напр. Director працює за розкладом без
живої людини поруч) — окреме рішення тоді, з окремим ADR.

**Прийнято (Антон, 2026-07-31): синхронна модель.** Одна CLI-команда,
підтвердження одразу в тому ж терміналі, весь граф в одному процесі.
Асинхронна модель (Postgres-checkpointer) — окреме рішення пізніше, коли
з'явиться реальний сценарій (Director без живої людини поруч), не зараз.

## 3. Формат трейсу (уточнення до резолюції #4, не було деталізовано в пропозиції)

JSON, один файл на прогін графа (`traces/<thread_id>.json`), масив кроків:

```json
{
  "thread_id": "...",
  "graph": "director",
  "steps": [
    { "node": "validate_demand", "status": "signal", "ts": "..." },
    { "node": "prepare_diff", "status": "ok", "ts": "..." },
    { "node": "approval_gate", "status": "waiting", "ts": "..." },
    { "node": "approval_gate", "status": "approved", "approver": "$(whoami)", "ts": "..." },
    { "node": "open_pr", "status": "applied", "pr_url": "...", "ts": "..." }
  ]
}
```

Мінімально достатньо для §2.1 (аудит) і для майбутніх evals (§1, п.5) —
не проектую формат наперед під зовнішній сервіс (LangSmith/OTel), як і
домовлено в резолюції #4.

## 4. Milestone-розбивка — без змін від пропозиції Code

`4a` (гейт + трейс) → `4b` (ретраї + ліміти + evals), acceptance criteria
розділу 3 вхідного документа лишаються канонічними, доповнюються тут:

- [ ] `reject` лишає diff-файл на диску (§2.1).
- [ ] Трейс містить `approver`/`ts` на кроці `approved` (§2.1, §3).
- [ ] Явне слово `approve` вимагається CLI, не одноклавішне підтвердження
      (§2.1).
- [ ] Синхронна модель задокументована в CLI `--help`: команда не повертає
      керування, поки не отримано approve/reject (§2.2).
