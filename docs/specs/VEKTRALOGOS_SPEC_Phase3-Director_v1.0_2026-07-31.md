## 2. Доповнення до резолюції #2: паралелізм воркерів (3b)

STRATEGY.md §3 Фаза 3 називає конкретну навчальну ціль: **«паттерн
координатора, handoff, спільний стейт, ПАРАЛЕЛІЗМ суб-агентів»**. Пропозиція
Code коректно описує branch-структуру (`route_to_workers` → 3 паралельні
гілки → `collect_results`), але не каже explicit, що ці гілки МАЮТЬ
виконуватись паралельно (LangGraph fan-out/fan-in), а не послідовно в циклі —
інакше 3b технічно працює, але навчальна ціль «паралелізм» не закрита.

> [!IMPORTANT] Додаю в acceptance criteria 3b: тест, що явно демонструє
> паралельне виконання Product/Marketing/Sales-Support воркерів (напр. через
> мокнуті воркери з штучною затримкою — сумарний час прогону графа < суми
> часів воркерів, що доводить fan-out, а не послідовний виклик).

Решта комунікаційного патерну (subgraphs + спільний `DirectorState`,
без окремого handoff-протоколу) — без змін від пропозиції Code.

## 3. Формат фікстура метрик — закриваю питання

Пропозиція Code запропонувала поля `installs, mrr, rating, churn`. Доповнюю
одним полем і фіксую логіку `validate_demand`, бо без явного порогу гейт —
просто parser, а не рішення:

```json
{
  "date": "2026-07-31",
  "installs": 0,
  "mrr_usd": 0,
  "rating": null,
  "churn_pct": null,
  "waitlist_signups": 4
}
```

**Чому додано `waitlist_signups`:** STRATEGY.md §4 прямо описує перший вузол
Director як «сканує 1★-відгуки конкурентів, вейтлист» — вейтлист явно
названий джерелом сигналу, окремо від власних installs/MRR. На цьому етапі
(до лістингу в App Store — STRATEGY §1a, крок 2 ще не пройдено) `installs` і
`mrr` в проді фізично = 0, тож якщо `validate_demand` дивиться лише на них —
гейт завжди `no_signal`, що безглуздо для навчальної фази. Вейтлист і
конкурентні відгуки (вже є фікстур з Ф2, `ingest_feedback`) — реалістичні
джерела сигналу ДО лістингу.

**Логіка `validate_demand` (детермінована, без LLM — консистентно з `pick_and_apply_fix` у Ф1/2a):**

```python
def validate_demand(metrics: Metrics, feedback: list[FeedbackItem]) -> bool:
    return metrics.waitlist_signups > 0 or len(feedback) > 0
```

Сигнал = є або вейтлист-заявки, або релевантні конкурентні відгуки
(переюз `ingest_feedback` з Ф2, не новий парсер). `installs/mrr/rating/churn`
лишаються в фікстурі для майбутнього (Ф4 — коли `installs > 0` стане
реальним порогом), але не беруть участі в логіці гейта Ф3 — це чесніше, ніж
удавати, що поріг на них є сенс мати вже зараз.
