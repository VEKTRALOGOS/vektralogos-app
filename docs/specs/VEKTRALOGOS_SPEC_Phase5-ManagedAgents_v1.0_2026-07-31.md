## 0. Резолюція на пропозицію Claude Code

Пропозиція коректно верифікована проти актуального API CMA (перевірила
незалежно — публічна бета, `$0.08`/session-hour + токени, container-per-
session, agents/sessions/deployments як окремі версійовані ресурси,
multi-agent orchestration у research preview — нам не треба, тут один агент
на сесію). Усі 6 резолюцій §1 і розбивка 5a/5b §3 — **затверджено без змін.**

Гейт вартості (§4 вхідного документа) — правильний за духом (той самий
approval-принцип, що Ф4), але для фінальної фази з реальними грошима
недостатньо конкретний. Доповнюю в §2.

## 1. Чому це фінал — без змін від пропозиції Code

Схеми 5a/5b (§2 вхідного документа) і термінальні стани (`idle`/`terminated`
→ `ok`/`needs_human`) — канонічні, переносити тут вдруге не буду.

## 2. Посилений гейт вартості (доповнення)

### 2.1 Два окремих "go", не один

Пропозиція просить одне підтвердження «перед першим реальним прогоном».
Розділяю на два, бо фінансовий профіль різний:

| | 5a (test-сесії) | 5b (`deployments.create`, cron) |
|---|---|---|
| Характер витрат | Кінцева кількість ручних прогонів, ти бачиш кожен | **Безстрокові**, доки deployment не вимкнено — рахунок росте самостійно, без нового твого рішення на кожен запуск |
| Ризик | Низький, обмежений | Вищий — «забутий» deployment продовжує тарифікуватись |

**Тому: окремий «go» для 5a і окремий, пізніший «go» для 5b.** Перший не
дає автоматичного дозволу на другий.

### 2.2 Формат запиту на "go" — конкретні числа, не відкрите питання

За аналогією з Ф4 §2.1 (explicit confirmation, не одноклавішне «ок»): запит
до Антона мусить містити ОЦІНКУ, не питати «який бюджет» відкрито (це
перекладає розрахунок на Антона, коли його мусить зробити Claude Code):

**Для 5a:** «N контрольних питань (з §3 вхідного документа Code), кожна
сесія ≈ X хв → оцінка $Y за весь прогін порівняння, за тарифом
$0.08/session-hour + токени claude-opus-5». Антон підтверджує суму, не
абстрактний «бюджет».

**Для 5b:** окрім оцінки вартості одного спрацювання deployment — явно
вказати **частоту cron** і **як/коли deployment буде вимкнено** після
завершення порівняльного ADR (§2.3). Без плану вимкнення — не питати «go».

### 2.3 Resource hygiene — обов'язковий teardown-крок

Відсутнє у пропозиції: після завершення 5a/5b жоден тестовий/порівняльний
ресурс (agent config, deployment) не повинен лишитись працювати мовчки і
тарифікуватись без мети.

> [!IMPORTANT] Acceptance-критерій до обох milestone: команда/крок, що
> перелічує й (за потреби) видаляє/вимикає створені CMA-ресурси
> (`agents.list`/`deployments.list` → delete/disable), задокументована в
> порівняльному ADR (§5, п.5 вхідного документа) як частина «результату
> фази», не залишена на потім.

## 3. Milestone-розбивка — без змін від пропозиції Code, з доповненим acceptance

**5a** — без змін від §3 вхідного документа, плюс:
- [ ] Запит на "go" містить конкретну оцінку вартості (§2.2), не відкрите
      питання.
- [ ] Після порівняння — тестовий agent config або видалений, або
      задокументовано, чому лишається (versioned config сам по собі не
      тарифікується — тарифікуються сесії; уточнити це в ADR явно, щоб
      Антон розумів, що саме коштує грошей).

**5b (стретч)** — без змін від §3, плюс:
- [ ] Окремий "go" від 5a (§2.1), з планом вимкнення cron-deployment (§2.2).
- [ ] Deployment вимкнено/видалено одразу після того, як порівняльний ADR
      написаний — не лишається «про запас».
